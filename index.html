0. Ce que tu dois savoir avant de commencer

Pas de panique : ce chapitre utilise beaucoup de sigles (SGA, PGA, PMON...), mais derrière, il n'y a que quelques idées simples. Avant de les voir, voici les bases dont tout le chapitre dépend.

Une base de données, c'est quoi ?
Une collection organisée d'informations (clients, produits, notes d'étudiants...) stockée de façon durable, en général sous forme de tables. Un logiciel appelé SGBD (système de gestion de base de données) la gère. Oracle est l'un de ces logiciels.
Le disque et la RAM (mémoire vive)
C'est l'idée la plus importante du chapitre. Le disque (SSD ou disque dur) garde les données même quand l'ordinateur est éteint, mais il est lent. La RAM est très rapide, mais elle s'efface à l'extinction. Oracle fait donc tout le temps la navette : il garde sur disque ce qui doit survivre, et il charge en RAM ce dont il a besoin tout de suite. Presque toute l'architecture Oracle découle de ce compromis.
Un processus
Un programme en cours d'exécution. Quand tu ouvres un navigateur, l'ordinateur crée un processus. Oracle en lance plusieurs en même temps, chacun avec un travail précis. Ceux qui travaillent sans que personne ne les voie s'appellent des processus d'arrière-plan (background).
Client et serveur
Le client est le programme que tu utilises (SQL Developer, sqlplus). Le serveur est le programme Oracle qui détient les données et répond. Le client envoie des demandes en SQL, le serveur répond. Ils peuvent être sur la même machine (localhost, comme dans ton cours) ou sur deux machines.
SQL
Le langage pour parler à une base : SELECT pour lire, INSERT, UPDATE, DELETE pour modifier. Les instructions qui modifient s'appellent LMD (langage de manipulation de données).
Un cache
Une réserve en RAM qui garde des copies de choses déjà utilisées, pour éviter de les relire sur le disque. C'est comme garder sur ton bureau les livres que tu consultes souvent plutôt que d'aller les chercher dans la bibliothèque à chaque fois.
L'algorithme LRU (Least Recently Used)
Quand le cache est plein, il faut jeter quelque chose. LRU jette l'élément utilisé il y a le plus longtemps. Logique : ce qu'on n'a pas touché depuis longtemps a peu de chances d'être redemandé.
Transaction, commit, rollback
Une transaction est un groupe d'opérations qui doivent réussir ensemble ou échouer ensemble (exemple : retirer 100 DH d'un compte et les ajouter à un autre). COMMIT valide, ROLLBACK annule et revient en arrière. Le chapitre parle de "cohérence des transactions" et de "undo" : c'est ce mécanisme.
Un fichier de données
Un simple fichier sur le disque (extension .DBF, .CTL...). Dans Oracle, une base de données n'est rien d'autre qu'un ensemble de fichiers.
L'analogie fil rouge : la bibliothèque La base de données, ce sont les livres rangés sur les étagères (des fichiers sur le disque). L'instance, c'est l'équipe de bibliothécaires avec leurs bureaux et leurs chariots de travail (des processus et de la RAM). Sans bibliothécaires, les livres sont inaccessibles. Sans livres, les bibliothécaires n'ont rien à gérer. Les deux ensemble forment le serveur Oracle.

L'instance est "un ensemble de structures mémoire qui gèrent les fichiers de la base et un ensemble de processus d'arrière-plan". La base de données est "un ensemble de fichiers qui stockent les données".

En multitenant, une seule instance ouvre un seul conteneur (la CDB, qui contient plusieurs PDB). page 11/55 Une instance = SGA + processus d'arrière-plan. Fonctions : exécuter les requêtes, gérer les entrées/sorties, maintenir la cohérence des transactions. En multitenant : une seule instance pour toute la CDB, partagée entre CDB$ROOT, PDB$SEED et les PDB. Avantages : mutualisation des ressources, meilleure performance, gestion simplifiée.

page 12/55 Les cinq identifiants d'une instance : DB_NAME (nom de la base dont dépend l'instance), SID (identifiant de l'instance), ORACLE_SID (variable d'environnement de l'OS qui précise à quelle instance se joindre), le fichier de paramètres (PFILE, texte) et le fichier de paramètres serveur (SPFILE, binaire). Les deux requêtes de la page, SELECT name FROM v$database; et SELECT instance_name FROM v$instance;, te donnent le nom de la base et celui de l'instance.

page 22/55 Règle à retenir : une instance ne peut être associée qu'à une seule base de données, mais une base de données peut utiliser plusieurs instances (c'est le principe de Oracle RAC, plusieurs serveurs sur la même base, pour la disponibilité). Mnémotechnique : un bibliothécaire ne travaille que pour une bibliothèque, mais une bibliothèque peut employer plusieurs bibliothécaires.

Processus serveur
Le processus côté Oracle qui travaille pour toi. Ovale bleu sur les schémas. Il lit, écrit et exécute tes requêtes. Il possède sa propre mémoire privée : la PGA.

page 14/55 Contexte local : Oracle 19c installé sur ta machine (localhost), accès par SQL Developer ou sqlplus, peu d'utilisateurs, objectif d'une base simple et facile à administrer.

Mode dédié ou mode partagé

page 15/55 En mode dédié, chaque session obtient son propre processus serveur. C'est comme avoir un serveur de restaurant rien que pour toi : performances stables, pas de dispatcher. C'est le mode par défaut et celui recommandé en localhost. page 16/55 En mode partagé, plusieurs clients se partagent un pool de processus serveurs, via des dispatchers qui répartissent le travail. C'est comme un serveur qui s'occupe de plusieurs tables : économique quand il y a beaucoup de clients, mais plus complexe, donc inutile sur une machine locale. L'image avec "Client 1 à 4" illustre un serveur qui répond à plusieurs clients.

page 17/55 Résumé : (1) établissement de la connexion, (2) création d'un processus serveur dédié ou partagé, (3) création d'une session. Les processus échangent via SQL*Net, et la session utilise la SGA et la PGA pour traiter les requêtes.

5. La base de données : les fichiers physiques

page 18/55 Une base Oracle est un ensemble de données traitées comme une seule entité, constituée de trois types de fichiers essentiels. Le schéma montre en orange la "Base de données CDB Oracle" avec ses trois groupes, et autour les fichiers annexes (paramètres, mots de passe, journaux archivés).

Fichiers de données (datafiles, .DBF)
Là où se trouvent tes tables, tes index et aussi le dictionnaire de données. C'est le "contenu" de la bibliothèque. Exemples vus page 23/55 : SYSTEM01.DBF, SYSAUX01.DBF, USERS01.DBF, UNDOTBS01.DBF, TEMP01.DBF.
Fichiers de contrôle (control files, .CTL)
De petits fichiers très importants : ils décrivent la structure de la base (noms et emplacements de tous les autres fichiers, état de la base). Sans eux, Oracle ne sait plus où est quoi. C'est le catalogue de la bibliothèque. On en garde plusieurs copies (CONTROL01.CTL, CONTROL02.CTL), par sécurité.
Fichiers de journalisation (redo log files)
Ils enregistrent toutes les modifications faites dans la base. C'est le registre où l'on note chaque changement : si la machine plante, Oracle relit ce registre pour rejouer ce qui n'avait pas encore été écrit dans les datafiles. Exemples : REDO01, REDO02, REDO03 (on les utilise en rotation).

page 25/55 (première diapositive, "Fichiers physiques") Elle ajoute deux fichiers : les fichiers archivés (copies des redo logs, créées uniquement en mode ARCHIVELOG, utiles pour restaurer la base jusqu'à un moment précis) et le fichier de paramètres (SPFILE ou PFILE) qui configure l'instance, par exemple la taille de la mémoire. Le fichier de mots de passe, vu sur le schéma, authentifie les administrateurs.

PiègeLe fichier de paramètres configure l'instance, mais il est stocké sur le disque. C'est lui qu'Oracle lit en premier au démarrage, avant même de créer la SGA.

6. Les structures logiques : comment les données sont rangées

page 25/55 (diapositives "Fichiers logiques") Les fichiers physiques sont vus de l'extérieur, par le système d'exploitation. À l'intérieur, Oracle organise l'espace de façon logique, avec une hiérarchie que montre le petit schéma à droite : Tablespace, puis Segment, puis Extent, puis Bloc.

Tablespace
Un "rayon" de la bibliothèque : un regroupement logique de segments. Un tablespace est stocké dans un ou plusieurs datafiles. Types principaux : SYSTEM (métadonnées de la base), SYSAUX (informations auxiliaires), UNDO (infos pour annuler les transactions), TEMP (espace temporaire pour les tris et les hash joins) et USERS/DATA (tables et index des utilisateurs).
Segment
L'espace occupé par un objet (une table, un index...). Types vus : segment de données (lignes de table), segment d'index, segment undo (anciennes valeurs, pour le rollback).
Extent
Une suite de blocs contigus alloués à un segment. Oracle n'alloue pas le disque octet par octet, mais par paquets, ce qui facilite la gestion de l'espace.
Bloc
La plus petite unité de stockage logique, de taille configurable (par exemple 8 Ko, paramètre DB_BLOCK_SIZE). C'est elle qui contient les lignes réelles. Quand Oracle lit le disque, il lit au minimum un bloc entier.

Analogie : tablespace = rayon, segment = collection d'une série de livres, extent = une étagère entière réservée, bloc = une page.

7. Les structures mémoire : SGA et PGA

page 26/55 Oracle utilise deux grandes zones de RAM. La SGA est allouée au démarrage de l'instance et partagée. La PGA est allouée au démarrage de chaque processus serveur et privée. Sur le schéma, chaque Server process a sa PGA, alors que la SGA (avec la taille maximale SGA_MAX_SIZE) contient Shared pool, Streams pool, Large pool, Java pool, Database buffer cache et Redo log buffer.

page 28/55 Analogie : la SGA est le grand tableau commun de la salle, que tous les bibliothécaires voient. La PGA est le carnet personnel d'un bibliothécaire : ses notes de travail, ses tris en cours, les variables de ta session.

Les trois blocs essentiels de la SGA

pages 31/55 à 38/55

1. Zone de mémoire partagée (Shared pool)
Elle stocke les dernières instructions SQL/PLSQL et les dernières définitions de données utilisées. Taille : paramètre SHARED_POOL_SIZE. Elle contient deux sous-caches. Le cache "library" garde les instructions SQL et PL/SQL récentes avec leur plan d'exécution, ce qui permet de partager une requête déjà analysée (gain de temps énorme), géré par LRU, avec une zone SQL partagée et une zone PL/SQL partagée. Le cache du dictionnaire de données (row cache) garde les définitions récentes (tables, colonnes, index, utilisateurs, privilèges). Au moment de l'analyse d'une requête, le processus serveur y vérifie que les noms d'objets existent et que tu as le droit d'y accéder. En 19c, chaque PDB profite d'optimisations pour un accès plus rapide à ses métadonnées.
2. Cache de tampons de la base de données (Database buffer cache)
Il garde des copies des blocs de données lus dans les datafiles. Quand tu lis ou modifies une ligne, Oracle travaille sur le bloc en RAM, pas sur le disque : gains de performance considérables. Géré par un LRU à plusieurs niveaux, il est partagé entre CDB et PDB. Il se découpe en sous-caches : DB_CACHE_SIZE (principal), DB_KEEP_CACHE_SIZE (ce qu'on veut garder), DB_RECYCLE_CACHE_SIZE (ce qu'on veut évacuer vite). Il peut être redimensionné dynamiquement (AMM ou ASMM), et DB_CACHE_ADVICE (ON, OFF, READY) collecte des statistiques consultables dans V$DB_CACHE_ADVICE pour savoir quelle taille serait idéale.
3. Tampon de journalisation (Redo log buffer)
Une petite zone qui note les modifications avant leur écriture dans les redo logs sur disque. Paramètre : LOG_BUFFER.

Les autres composants de la SGA

pages 29/55 et 30/55 Large Pool (optionnel : RMAN pour les sauvegardes, exécution parallèle), Java Pool (procédures Java stockées), Streams Pool (réplication), Flashback Buffer (Flashback Database), In-Memory Area (stockage en colonnes pour accélérer l'analyse), Memoptimize Pool (accès rapide clé-valeur), Shared I/O Pool, Database Smart Flash Cache (extension sur disque flash, optionnelle) et Fixed SGA (variables internes d'Oracle). Pour un premier examen, concentre-toi sur les trois blocs ci-dessus.

page 31/55 Les paramètres de taille de la SGA : SGA_MAX_SIZE (maximum), SHARED_POOL_SIZE, DB_CACHE_SIZE, LOG_BUFFER, LARGE_POOL_SIZE, JAVA_POOL_SIZE. La SGA contient aussi les verrous (lock) et les latchs, des mécanismes pour empêcher deux processus de modifier la même chose en même temps.

La PGA

page 28/55 Mémoire privée de chaque processus serveur, utilisée pour les tris, les hash joins et les variables de session. Gestion automatique par MEMORY_TARGET, SGA_TARGET et PGA_AGGREGATE_LIMIT.

8. Les processus d'arrière-plan

Les diapositives les nomment (ovales jaunes en bas de l'instance sur les pages 1/55, 3/55, 4/55 et 9/55) sans les détailler encore. Voici ce que tu dois savoir de chacun, ce sera utile pour la suite du cours.

DBWR / DBWn (Database Writer)
Écrit sur disque les blocs modifiés du buffer cache, mais pas à chaque modification : il le fait en groupe, de façon différée, pour être efficace.
LGWR (Log Writer)
Écrit le contenu du redo log buffer dans les redo logs. Il écrit notamment au COMMIT. C'est la garantie que ta transaction validée ne sera jamais perdue.
CKPT (Checkpoint)
Signale régulièrement un point de repère : tous les changements jusqu'ici sont sur disque. Il met à jour les fichiers de contrôle et les en-têtes des datafiles. Il raccourcit la récupération après une panne.
SMON (System Monitor)
Le "réparateur" : au démarrage après un arrêt brutal, il effectue la récupération de l'instance, et il nettoie l'espace temporaire.
PMON (Process Monitor)
Le "nettoyeur de sessions" : si un processus utilisateur meurt, il annule sa transaction et libère ses ressources (verrous, mémoire).
Comment tout cela s'enchaîneTu fais un UPDATE : le processus serveur lit le bloc dans le buffer cache (en le chargeant depuis le datafile si besoin), le modifie en RAM, et note le changement dans le redo log buffer. Au COMMIT, LGWR écrit le redo sur disque. Plus tard, DBWR écrit le bloc modifié dans le datafile. CKPT marque la progression. Si tout plante entre-temps, SMON utilise les redo logs au redémarrage pour tout remettre en ordre.

9. L'architecture multitenant (CDB et PDB)

Avant Oracle 12c, chaque base avait sa propre instance : dix bases, dix instances, donc dix fois la mémoire et dix fois les processus. Le multitenant résout cela. Analogie : au lieu de construire dix maisons avec chacune sa chaudière, on construit un immeuble avec une seule chaudière (l'instance) partagée par des appartements indépendants (les PDB).

CDB (Container Database)
L'immeuble entier, la base "conteneur". Une CDB a une instance, une SGA et des processus de fond.
CDB$ROOT
La racine : le local technique. Elle contient les métadonnées communes et les utilisateurs communs.
PDB$SEED
L'appartement modèle, en lecture seule. Oracle le copie pour créer rapidement une nouvelle PDB.
PDB (Pluggable Database)
Un appartement : une base logique autonome qui a ses propres objets et schémas, et se comporte comme une base indépendante. Elle peut être "branchée" ou "débranchée" (d'où "enfichable") et déplacée vers une autre CDB. Exemples de la page 4/55 : PDB1 pour "RH", PDB2 pour "VENTES".

page 19/55 Chaque PDB possède ses propres objets et schémas. Les datafiles de chaque PDB sont rangés dans leur dossier (orclpdb, pdb2, pdbseed, page 23/55). Les fichiers de contrôle et les redo logs, eux, sont communs à la CDB.

Avantages : mutualisation des ressources, meilleure performance, gestion centralisée (une sauvegarde, une mise à jour pour toute la CDB) et isolation logique entre les PDB.

10. Résumé et pièges d'examen

À savoir par coeur Serveur Oracle = Instance + Base de données.
Instance = SGA + PGA + processus de fond (RAM et processus).
Base de données = datafiles + controlfiles + redo logs (disque).
Connexion = processus utilisateur, puis processus serveur, puis session.
Hiérarchie logique : Tablespace, Segment, Extent, Bloc.
Multitenant = une instance, une CDB, plusieurs PDB.
Pièges fréquents 1. Ne pas confondre instance et base : l'une est en RAM, l'autre sur le disque.
2. SGA = partagée par tous. PGA = privée à chaque processus serveur.
3. Une instance n'ouvre qu'une base, mais une base peut avoir plusieurs instances.
4. Le mode dédié est le mode par défaut et le bon choix en localhost.
5. Le Shared pool contient le cache library ET le cache du dictionnaire de données.
6. Le buffer cache stocke des blocs de données, le redo log buffer stocke des modifications.

Auto-test rapide

Essaie de répondre sans regarder : Que se passe-t-il quand on coupe l'instance, que reste-t-il ? Pourquoi existe-t-il deux caches différents dans le Shared pool ? Quel processus écrit au COMMIT ? Pourquoi le multitenant économise-t-il de la mémoire ?
